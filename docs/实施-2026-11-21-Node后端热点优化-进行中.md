# 实施：Node 后端热点优化（不换技术）

> 目标：更快、更省资源，技术栈不动。四个真实瓶颈按收益排序，分 4 个主题批次 + 1 个收尾批次，每批独立可验收、一次提交。
> 背景：全量摸底后端（13,477 行纯 Node 标准库，零运行时依赖）后与用户确认走「优化现有实现」路线，Rust 重写方案已否。

## 目标

| # | 瓶颈 | 现状 | 之后 |
| --- | --- | --- | --- |
| 1 | 盘扫描阻塞主线程 | `dirScan` 同步递归 readdir+stat，大库每 30s 一个请求吃 100~300ms | `worker_threads` 专用线程，主线程不碰 |
| 2 | FCPXML 打包冻结全代理 | `createZip` 主线程 `deflateRawSync` + 全包攒内存（素材门 512MB/个） | 流式 + 异步 deflate，内存 ≈ 单条目 |
| 3 | state.json 写路径 | 每次写键全键重序列化 + 全量 sha256 + 原子写四步 | 逐键碎片缓存，只重序列化变更键；同内容写零落盘 |
| 4 | relay 大请求体 | `readBody` 全量缓冲，上传端点 128MB 峰值 | 超阈值 POST/PUT 流式直通 |

## 范围与纪律

- 只动 `server/` 与对应判据；页面 / 前端不动。
- 每批提交前 `npm run check` + `npm run test` 全绿；浏览器 e2e 不是前置。
- 批次 1 的签名一致性（worker 产出 `sig` 与 `sampleSigOfBuffer` 逐字节一致）必须有夹具测试。
- 批次 3 的序列化输出必须与现实现逐字节一致（checksum 兼容旧 state.json / 快照恢复 / 云同步）。
- 明确不做（收益/风险比不划算）：`UV_THREADPOOL_SIZE` 调整、静态压缩缓存上限（当前 ~百份压完一两 MB，192 条上限够用）、`loadEnvFile` 每请求 stat（已是 1 次 syscall ≈22µs）、keepAliveTimeout 调优（回环握手成本可忽略）。
